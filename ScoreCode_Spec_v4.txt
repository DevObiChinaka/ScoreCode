SCORECODE
Project Specification & Architecture Document
Version 4.0 — Agent Ready  |  March 2026  |  Desktop Exam Management System

Scope
ScoreCode is a secure desktop exam management system for CS students. Lecturers create and publish exams. Students take exams in a controlled environment. Submissions are graded via AI-assisted or manual review. The system is built on WPF (.NET 8), ASP.NET Core, PostgreSQL, and Monaco Editor — with a one-week intensive build target for v1.
This document is the definitive reference for architecture, feature scope, data models, user flows, API contracts, UI layouts, and build phases. It is written to be handed directly to an AI coding agent. Every decision is already made — the agent should build, not design.

SECTION 1
Roles & Permissions
Three roles exist. Each has a distinct client surface and permission boundary.

RoleCore PermissionsCannot DoAdminCreate/deactivate user accounts; assign lecturers to courses; view system health; export audit logs; manage server configCreate or modify exams; access student code directlyLecturerCreate exams; write questions and marking guides; select eligible students; publish/unpublish exams; view all submissions; run AI or manual grading; release results; extend time for studentsEdit student profiles (Admin only); access another lecturer's examsStudentView published exams assigned to them; take exams; write and run code; submit before timer endsView other students' submissions; access the system outside an active exam session; modify their own profile (Admin only)
Key Rules
• Only a Lecturer can create, modify, publish, or unpublish an exam.
• An exam must be published before any student can see or access it.
• Students can only see exams they are explicitly assigned to.
• Student programme information is immutable. Level can be updated annually by Admin.
• One active session per student at any time (enforced server-side).
• Admins cannot take exams or grade submissions.


SECTION 2
Lecturer Workflows
Why this comes first: Students cannot take an exam that does not exist. The entire student workflow depends on lecturers completing these steps first. Every feature in this section is a prerequisite for Section 3.
2.1  Creating an Exam
The exam builder is the core of the lecturer interface. It is a multi-step form that produces an exam record on the server.
Step 1 — Exam Metadata
• Exam title (e.g. 'CSC 301 Mid-Semester Practical')
• Course code
• Scheduled date and start time
• Duration in minutes (e.g. 90)
• Programming language(s) allowed — multiselect from: Python, Java, C++, JavaScript, HTML/CSS
• IntelliSense enabled/disabled toggle
• Grading mode: AI-assisted | Manual | Both (lecturer decides per exam)
Step 2 — Assign Students
• Lecturer searches by name, matric number, department, or level.
• Select individual students or an entire class group.
• Assigned students list is saved and editable until the exam is published.
• Only assigned students will see this exam in their client.
Step 3 — Add Questions
Each question is a self-contained record with these fields:
• Question number (auto-incremented, reorderable)
• Question text (rich text — supports code blocks, images)
• Total marks for this question
• Expected language (can differ per question if multi-language exam)
• Marking guide — free text field the lecturer fills out, e.g:
"Expect a for-loop or while-loop iterating n times. Award 2 marks for correct loop structure. Award 2 marks if variable names are meaningful. Deduct 1 mark for each syntax error. Award 1 mark for correct output format. Award 1 bonus mark if student handles negative input edge case."
• This marking guide is sent verbatim to the AI grader and shown to the manual grader.
• Multiple questions per exam. No hard limit — reasonable limit is 10 for a 90-minute exam.
Step 4 — Review & Publish
• Lecturer sees a preview of the full exam as students will see it.
• Exam status: Draft | Published | Active | Closed.
• Draft — only visible to the lecturer. Editable.
• Published — visible to assigned students. No longer editable (except adding time extension).
• Active — exam is currently running. Timer is live.
• Closed — no new submissions accepted. Grading phase.
Important: Publishing is irreversible unless the exam has zero submissions. Once a student has started, the exam cannot be edited or unpublished — only extended or closed.

2.2  Starting an Exam
Publishing an exam does not start it. The exam window opens automatically at the scheduled start time, or the lecturer can manually trigger it early.
5. Exam reaches scheduled start time (or lecturer clicks 'Start Now').
6. Server broadcasts exam-start signal to all assigned students' clients via SignalR.
7. Student client receives signal, locks into exam mode (fullscreen, anti-cheat active).
8. Server delivers encrypted exam payload to each student client.
9. Student timers begin. They are server-authoritative — not client clocks.

2.3  Monitoring During an Exam
The lecturer's live dashboard shows, in real time:
• Each student: status (waiting, active, submitted, timed-out, flagged).
• Cheating events: focus loss, process switch attempt, window minimize attempt — each timestamped.
• Submission count vs total students.
• Timer countdown (same server clock as students).
Actions available during the exam:
• Add time for a specific student (e.g. +10 minutes for a genuine technical issue).
• Force-submit a student's current autosave (emergency).
• Flag a student for review (adds to audit log).
• End the exam early (closes all active sessions, triggers auto-submit for anyone still in progress).

2.4  Grading Submissions
After the exam closes, the lecturer accesses the grading dashboard.
AI-Assisted Grading Mode
For each submission, the system sends to the configured AI model (Claude or GPT-4o):
• The exam question text
• The marking guide written by the lecturer
• The student's submitted code
• The total marks available
The AI returns a structured JSON response:
{ "score": 14, "max_score": 20, "feedback": ["Loop structure is correct (+4)", "Variable names are not descriptive (-2)", "Output format matches expected (+3)", "Syntax error on line 7 (-1)"], "criteria_results": [{"criterion": "Loop structure", "awarded": 4, "max": 4}, ...] }
Lecturer sees: the student's code, the AI score, and the AI's line-by-line reasoning. Lecturer can:
• Accept — AI score stands as final grade.
• Override — change any criterion score with a written reason (logged).
• Flag for manual — escalate to full manual review.
Manual Grading Mode
Lecturer reads the student's code directly alongside the marking guide. The same score breakdown form is shown — same fields, same criteria — but filled by the lecturer instead of AI. Useful for complex questions, dispute resolution, or when the lecturer prefers not to use AI.
Result Release
• Lecturer chooses when to release results — not automatic.
• Per-exam toggle: release to all students simultaneously.
• Students see: total score, per-question breakdown, feedback text.
• Students do not see: the marking guide, AI prompts, or other students' scores.


SECTION 3
Student Workflows
Prerequisite: None of the following is possible until a Lecturer has created an exam, assigned the student, and published it. The student dashboard will be empty until that has happened.
3.1  Pre-Exam (Waiting State)
• Student logs into ScoreCode client. Sees their upcoming exams list.
• Each exam shows: title, course, scheduled time, duration, status.
• Exam status shown as: Upcoming | Starting Soon (15 min warning) | Active | Completed.
• Client polls server every 60 seconds to check exam state. If SignalR connection is live, receives push notification instead.
• Student cannot enter exam mode until the exam is in Active state.
3.2  Exam Start
10. Student clicks 'Enter Exam' when exam becomes active.
11. Client receives full exam payload from server (questions, config, exam token, timer baseline).
12. Anti-cheat mode activates: fullscreen, keyboard hooks, process monitoring.
13. Monaco editor loads with the configured language and IntelliSense setting.
14. Timer starts (synchronized with server clock).
15. From this point, client operates autonomously — network not required for the exam itself.
3.3  During the Exam
• Questions are displayed in a tabbed or scrollable panel alongside the code editor.
• Student writes code in the Monaco editor.
• Run button executes code locally in a sandboxed process (Job Objects enforced — 5s CPU, 256MB RAM).
• Output (stdout, stderr, exit code) shown in a panel below the editor.
• Autosave runs every 5 seconds to local encrypted SQLite. No network required.
• Timer always visible in status bar. Color: green ? amber (10 min) ? red (5 min).
• Focus-loss events (window switch attempts, etc.) are logged and sent to server.
3.4  Submission
• Student clicks 'Submit Exam'. Two-stage confirmation modal appears.
• Modal shows: question count, files included, time remaining. Student confirms.
• Submission record is finalized locally: code + session nonce + student ID + timestamp ? SHA256 hash.
• Submission is encrypted and queued for upload.
• If online: uploads immediately. Server verifies hash and nonce. Returns confirmation ID.
• If offline: queued in SQLite. Uploads automatically when network is restored.
• After submission: editor becomes read-only. Student sees 'Submitted' state with confirmation ID.
3.5  Exam End (Timer Expired)
• 60-second countdown modal appears at 1 minute remaining.
• At 0:00: auto-submit triggers with last autosaved state.
• Anti-cheat mode deactivates. Client returns to normal state.
3.6  Viewing Results
• Results tab shows 'Pending release' until lecturer publishes grades.
• On release: student sees total score, per-question breakdown, and feedback.

SECTION 5
Code Execution
5.1  During Exam (Student Machine)
When the student presses 'Run', code executes locally. This is safe — students can only harm their own machine.
• Process is spawned via ProcessStartInfo with restricted working directory.
• Windows Job Object applied: 5 second CPU time limit, 256 MB memory limit.
• Process killed automatically if limits exceeded. Student sees 'Timed out' or 'Memory exceeded'.
• Stdout and stderr captured and displayed below the editor within 500ms of completion.
LanguageExecution CommandNotesPythonpython.exe <tempfile.py>Python 3.x must be installed on exam machine.Javajavac <File.java> && java <ClassName>JDK required on exam machine.C++g++ -o temp.exe <file.cpp> && temp.exeMinGW/GCC required on exam machine.JavaScriptnode.exe <file.js>Node.js required on exam machine.HTML/CSSLaunch in embedded WebView2 controlNo external dependency. Rendered in-app.Deployment note: All required runtimes (Python, JDK, Node.js, GCC) must be installed on exam machines before exam day. Include a pre-exam machine check tool in the admin panel.
5.2  During Grading (Lecturer Machine / Server)
Lecturers do not run code locally for grading. Code is sent to the AI grader as text, and the AI evaluates structure, syntax, logic, and adherence to the marking guide — without execution. This is by design: grading is based on code quality, not output.
If a lecturer wants to test-run a specific submission manually, they can use a separate 'Run in Sandbox' button which sends the code to a server-side execution endpoint (Phase 2: Judge0 integration).


SECTION 6
AI Grading System
Core insight: Grading is not based on whether the code runs or produces correct output. It is based on code quality: structure, syntax awareness, logic, variable naming, error count, and adherence to the marking guide. AI is well-suited to this.
6.1  How It Works
When a lecturer triggers AI grading for a submission, the server constructs and sends the following prompt to the configured AI model:
System: You are a CS examiner grading a student's code submission. Be fair, consistent, and specific.  Question: [question_text]  Marking Guide: [lecturer_marking_guide]  Total Marks: [max_marks]  Student's Code: [submitted_code]  Return ONLY valid JSON in this format: { "score": <int>, "max_score": <int>, "feedback": [<string>], "criteria_results": [{"criterion": <str>, "awarded": <int>, "max": <int>, "comment": <str>}] }
6.2  What the AI Evaluates
• Correctness of overall approach and algorithm logic
• Syntax — number and type of errors present
• Code structure: use of appropriate constructs (loops, functions, classes as required)
• Variable and function naming conventions
• Adherence to specific criteria in the marking guide
• Edge case handling if mentioned in the marking guide
• Code readability and organization
The AI does not execute the code. It reads and evaluates it as a human examiner would.
6.3  AI Model Configuration
ProviderModelNotesAnthropic (recommended)claude-sonnet-4-20250514Excellent at structured code analysis. Returns consistent JSON.OpenAI (alternative)gpt-4oStrong alternative. Same prompt format works.• API key stored in server environment config (never in client).
• Grading calls happen server-side only. Client never contacts the AI API directly.
• Each grading call is logged: model used, prompt sent (anonymised), response received, timestamp.
6.4  Lecturer Override
• Lecturer sees the AI's score and justification for every criterion.
• Any criterion score can be overridden. A reason field is required for overrides.
• Override is logged with: original AI score, new score, reason, lecturer ID, timestamp.
• Final grade = combination of AI scores (accepted) + lecturer overrides.

SECTION 9
Installer & Bundled Runtimes
Core principle: ScoreCodeSetup.exe is completely self-sufficient. After running it, ScoreCode works on any Windows 10/11 machine with zero additional setup — no internet, no IT pre-configuration, no runtime installs.
9.1  Why Bundle Runtimes
ScoreCode supports code execution in Python, Java, C++, JavaScript, and HTML/CSS. Rather than requiring exam machines to have these installed separately — risking version conflicts, missing runtimes, wrong PATH entries — ScoreCode bundles portable/embeddable versions of every runtime inside the installer. The app calls its own private copies using absolute paths. The machine's system PATH is entirely irrelevant.
This also removes the need for any pre-exam machine check for runtimes. Everything is guaranteed to be present because the installer put it there.
9.2  Installer Contents

9.3  How the App Calls Runtimes
The app never calls python, java, or node by name. It always uses absolute paths to bundled executables via a static constants class:
public static class RuntimePaths {     private static readonly string Base =         Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "runtimes");      public static string Python => Path.Combine(Base, "python", "python.exe");     public static string Node   => Path.Combine(Base, "node",   "node.exe");     public static string Java   => Path.Combine(Base, "jdk",    "bin", "java.exe");     public static string Javac  => Path.Combine(Base, "jdk",    "bin", "javac.exe");     public static string Gpp    => Path.Combine(Base, "mingw",  "bin", "g++.exe"); }
If a runtime folder is missing or corrupt, the app shows a specific error: 'Python runtime not found. Please reinstall ScoreCode.' — not a generic crash.

Context: Target: 20 hrs/day for one week. Phases are ordered by dependency — each phase produces a working, testable system. Lecturer features always precede the student features that depend on them.
Phase 1 — Foundation: Auth + Lecturer Exam Creation (Days 1–2)
Goal: Lecturer can log in, create an exam with questions and marking guides, assign students, and publish it. Admin can create user accounts. Student logs in and sees the published exam in their list.
Why this is first: Every student feature in every subsequent phase depends on an exam existing and being published. Nothing else can be tested or built without this foundation.
Server
• ASP.NET Core project scaffolding. PostgreSQL + EF Core setup. Docker Compose config.
• POST /auth/login ? JWT access token (15 min) + refresh token.

• Login screen.

Client — Lecturer
• Login screen ? JWT stored in encrypted SQLite.
• Dashboard: list of my exams with status badges (Draft / Published / Active / Closed).
• Exam Builder wizard — 4 steps:
? Step 1 Metadata: title, course code, scheduled date/time, duration (minutes), allowed language(s), IntelliSense on/off, grading mode (AI / Manual / Both).
? Step 2 Assign Students: search by name or matric number, select individuals or whole class groups.

Client — Student
• Login screen.
• Dashboard: list of exams assigned to me. Shows title, course, scheduled time, duration, status badge.

Phase 2 — Core Exam Loop: Taking + Submission (Days 2–4)
Goal: Student enters a published+active exam, writes code in Monaco, runs it using bundled runtimes, autosaves locally every 5 seconds, and submits. Submission arrives at the server. Lecturer can view it.
Dependency: Phase 1 complete. Exam must exist, be published, and student must be assigned.
Server
• POST /sessions/start ? validate student + exam, issue exam-scoped token + session nonce, return full exam payload.
• POST /sessions/heartbeat ? update last_heartbeat_at. Server flags (not terminates) sessions missing 3 heartbeats.
• GET /exams/{id}/payload ? encrypted exam content: questions, config, nonce, server timestamp.
• POST /submissions ? accept per-question submission, verify SHA256 hash, store. Return confirmation ID.
• GET /exams/{id}/submissions ? lecturer view: student list with per-question submission status.
• GET /submissions/{id} ? full code, question text, marking guide, metadata.
Client — Student
• 'Enter Exam' button active when exam status = Active. Click ? POST /sessions/start ? receive payload.
• Fullscreen mode activates (WindowStyle=None, Maximized, Topmost). Monaco editor loads.
• Question panel alongside editor: question text and marks shown. Tabbed if multiple questions.
• Autosave: every 5 seconds to local SQLite. AES encrypted. Zero network involvement.
• Run button: spawn bundled runtime via RuntimePaths constant. Windows Job Objects: 5s CPU, 256MB RAM. stdout/stderr/exit code shown in output pane below editor.
• Timer in status bar: always visible. Color: green ? amber at 10 min remaining ? red at 5 min.
• Submit: 'Submit Exam' ? confirmation modal (question count, time remaining) ? Confirm ? finalize locally ? SHA256 hash ? queue ? upload. Offline queue retries with backoff.
• Post-submit: editor becomes read-only. 'Submitted' state shown with server confirmation ID.
Client — Lecturer
• Submissions dashboard on exam detail page: table of assigned students, per-question status columns.
• Click any student/question cell ? view their code alongside question text and marking guide.

Phase 3 — AI Grading (Days 4–5)
Goal: Lecturer triggers AI grading per submission. AI evaluates code structure, syntax, logic, and marking guide adherence — not output. Structured score returned. Lecturer accepts or overrides. Results releasable to students.
Dependency: Phase 2 complete. Submissions must exist.
Server
• POST /grades/ai/{submission_id} ? build prompt (question + marking guide + code + max marks) ? call Claude API ? parse JSON ? store in grades table with full audit fields.
• PUT /grades/{id}/override ? change criterion score. reason field required. Logged with lecturer ID + timestamp.
• GET /exams/{id}/grades ? summary: each student, each question, total score, grading status.
• POST /exams/{id}/release-results ? mark all grades released. Students can now see scores.
Client — Lecturer
• Submission view: 'Grade with AI' button. Loading state shown during API call (3–10 seconds typical).
• Grade display: per-criterion table (criterion, max marks, AI marks, AI comment). Total score. Accept button.
• Override: click any criterion row ? editable score field + reason text ? Save. Override logged.
• Manual grading mode: same per-criterion table, all fields blank, filled by lecturer. No AI call.
• Exam overview: 'Release Results' button. Confirmation required. Irreversible.
Client — Student
• Results tab on exam card: 'Pending release' until lecturer releases.
• After release: total score, per-question score, per-criterion feedback text.

Phase 4 — Real-Time + Anti-Cheat Hardening (Days 5–6)
Goal: SignalR replaces all polling. Exam start/stop broadcasts simultaneously to all assigned students. Cheating events reach lecturer live. Keyboard hooks suppress OS-level window switching.
Dependency: Phases 1–3 stable. SignalR is purely additive.
Server
• SignalR ExamHub: clients join group by exam_id on connect.
• Server broadcasts: ExamStarted(examId), ExamEnded(examId), TimerSync(examId, remainingSeconds), CheatEvent(examId, studentId, eventType, timestamp), SubmissionReceived(examId, studentId).
• Lecturer sends to hub: StartExam(examId), EndExam(examId), ExtendTime(examId, studentId, extraMinutes).
Client — Student
• Replace 60-second status polling with SignalR listener. Exam activation is instant push.
• Receive TimerSync every 60 seconds to correct local clock drift.
• Low-level keyboard hook (SetWindowsHookEx WH_KEYBOARD_LL, requires admin): suppress Win, ALT+TAB, Win+Tab, Win+Ctrl+D, Win+D, Win+L, CTRL+ESC.
• Process monitor: terminate blocklisted apps (browsers, IDEs) on exam start. Log any new process launch attempts. Each event sent to server via SignalR immediately.
Client — Lecturer
• Live monitoring dashboard: real-time student status. No manual refresh needed.
• Cheating event feed: timestamped log. Flagged students highlighted in red.
• 'Start Exam Now' / 'End Exam Early' buttons send SignalR broadcast to all students.
• 'Add Time' per student: input extra minutes ? SignalR ExtendTime ? student timer updates live.

Phase 5 — Installer + Polish + Edge Cases (Day 7)
Goal: Fully installable, end-to-end working system hardened against common failure scenarios.
Installer Build
• Download the four portable runtimes: Python 3.12 embeddable (python.org), Node.js 20 LTS zip (nodejs.org), Eclipse Temurin 21 JRE zip (adoptium.net), WinLibs GCC 13 zip (winlibs.com). Place in runtimes\ folder.
• Run dotnet publish with self-contained + single-file flags.
• Write ScoreCode.iss (see Section 9.4). Build in Inno Setup Compiler ? ScoreCodeSetup.exe.
• Test on a clean Windows VM with nothing pre-installed. Verify all 5 languages execute correctly.
Edge Cases & Polish
• Crash recovery: on restart mid-exam, restore last autosave and remaining timer from local SQLite.
• Auto-submit at timer end: 60s countdown modal, then graceful auto-submit of last autosave.
• Accessibility: font size slider, high-contrast toggle in student preferences. Persisted in SQLite.
• Error handling: every failure state has a specific user-facing message. No generic crashes. No silent failures.
• appsettings.json: server URL externally configurable. Test changing it without rebuild.
• Load test: 30 concurrent simulated student sessions submitting simultaneously. Fix regressions.

SECTION 15
Summary
ScoreCode is a one-week intensive build for a deployable, defensible CS exam system. The architecture is solid. All decisions are made. The key principles to hold onto throughout the build:

• Lecturer first. Always. An exam must be created and published before any student feature can function.
• The installer is self-sufficient. One ScoreCodeSetup.exe — all language runtimes bundled, no prerequisites on exam machines.
• The app calls its own runtimes. System PATH is irrelevant. RuntimePaths constants are the only way code execution is invoked.
• The exam payload is self-contained. Once delivered at exam start, the client runs autonomously — network not required for the exam itself.
• Grading is qualitative, not output-based. AI reads and evaluates code against the marking guide the way a human examiner would.
• Autosave is local only. Sync is event-driven (submit trigger or restore trigger). Never autosave over the network.
• Anti-cheat is deterrence and evidence. Build the audit trail well. Accept that it cannot be a hard barrier.
• SignalR is the nervous system. Exam control, live alerts, timer sync, and submission status all flow through it.
• The Anthropic API key lives on the server only. It never touches a client machine.
• Defer aggressively. A complete, working v1 is worth more than a half-built v2.
